Brand strategy

What Cyferio actually is, in one sentence

Everything else in this document — the logos, the taglines, the site copy — is downstream of getting this sentence right first.

Cyferio is a self-hosted operations layer for OpenVPN — it takes a server that only knows how to authenticate connections, and turns it into something an IT team can actually govern: who connects, from which device, from where, using how much bandwidth, with a full record of every change.

That's the honest one-sentence version, based on what the product already does today (dynamic RBAC, MAC-address binding, connect-time geo/ASN/IP enforcement, hard bandwidth-quota enforcement, team-based reporting, a full audit log, and a self-service portal for end users). The brand should sell exactly this — not a vaguer "VPN for everyone" promise the product doesn't need to make.

What it is

A self-hosted admin & governance console that wraps OpenVPN — not a new VPN protocol, not a mesh network, not a managed cloud service.

Who it's for

MSPs running VPN for multiple clients, internal IT/security teams, and any org that needs self-hosted control (data sovereignty, compliance) without building admin tooling from scratch.

Why they'd choose it

No per-seat fees, no vendor lock-in, no re-architecting onto a mesh network — governance features that competitors either don't ship natively or gate behind enterprise/plugin tiers.

Brand guidelines

If Concept A ships, here's the system

Full guidelines below assume Cipher Signal (A) as the direction — the one I'd actually recommend, for the reasons in the recommendation banner. If you pick a different concept, this section gets rebuilt around that palette instead; the structure stays the same.

Why A, specifically: it's the only one of the five that's simultaneously distinctive (nothing else in the comparison table above looks like it), technically literal (signal/cipher, not a generic lock or globe), and dark-mode-native by default — which matters, since the product itself is an admin console IT staff will have open all day.

Color

Dark-first by design — light mode inverts to a cool white ground (#F7F9FC) with the same cyan/amber accents desaturated slightly so they don't vibrate against white.

Typography

Display: a geometric sans at tight negative tracking for headlines — think the weight of Söhne or Neue Montreal, not the two "safe AI-brand" defaults (Inter, Space Grotesk).

Body: a plain, highly-legible sans at 16–18px — this is a technical product, body copy should disappear, not perform.

Data/UI labels: monospace for anything numeric or code-adjacent (bandwidth figures, MAC addresses, audit-log entries) — reinforces "this is a real technical tool," and doubles as a visual signature distinct from competitors.

Visual style

  • Dark-mode-first UI chrome; light mode is a real second theme, not an afterthought
  • Concentric-ring motif reused sparingly as a loading/status indicator, not just the logo
  • No lock icons, no globe icons, no generic "shield" clip-art — the mark itself carries the security meaning
  • Screenshots/UI mockups get real data density — this brand doesn't hide behind whitespace, it's for people who read dashboards all day

What this palette is NOT

  • Not the cream-and-terracotta "warm SaaS" look every AI-assisted brand defaults to
  • Not a purple-to-blue gradient hero — the accent is a single confident cyan, used flat
  • Not rounded-everything — corners are tightened (8–10px), not the generic 16px "friendly" default
Website

Cloudflare Pages, not raw Workers

You asked for a recommendation between the two — here's the actual reasoning, not just the answer.

Use Cloudflare Pages, with Pages Functions for the one dynamic piece (the contact form).

Pages is purpose-built for exactly this: a static/SSG marketing site with git-based deploys, automatic preview URLs per branch/PR, and zero-config CDN caching. Plain Workers is a general-purpose edge-compute runtime — the right tool if you're building an API or heavy request-time logic, but it means hand-rolling asset serving, routing, and preview deployments that Pages already gives you for free. Pages Functions run on the same Workers runtime under the hood, so you're not giving anything up — you get the static-site ergonomics of Pages and the ability to drop in a serverless function exactly where you need one (the contact form's email-send endpoint, and later, a signup-waitlist API if you add one).

Static build

Astro or plain Vite + a templating layer — no client-side framework needed for a marketing site this size. Ships near-zero JS, which matters for the SEO/performance requirement you listed.

Dynamic pieces

Contact form → Pages Function → email via Resend/Postmark/SES. Optional waitlist signup → same pattern, written to D1 or a Google Sheet via API, whichever's less setup overhead for a v1.

What actually needs to change in the repo

Good news found while scoping this: the app already reads its display name from a Settings → Organization value (app_settings.app_name), used throughout templates and emails — so most of the in-product rebrand is a config change, not a find-and-replace sweep. The checklist below separates the two.

Default app_name → "Cyferio"Config default change — covers page titles, email templates, sidebar footer credit, and every other place that already pulls from this setting.
README.mdFull rewrite — project name, description, screenshots, install instructions.
Login page brandingCheck for any hardcoded product name outside the app_name-driven template — confirm during implementation, not assumed clean.
Repository name / GitHub orgYour call — renaming the repo breaks existing clone URLs/CI references unless redirects are set up; worth deciding deliberately, not as a side effect.
Docs / comments referencing the old working nameSweep code comments and docs/*.md for the old project name used as prose (not the app_name variable itself) — cosmetic, low priority, can trail the main rebrand.
ScreenshotsAnywhere currently showing the old default app_name in the UI needs a retake once the default changes.
